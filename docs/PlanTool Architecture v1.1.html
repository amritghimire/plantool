PlanTool Engineering OS, v1.1

One product with two ways to work. You drive Personal mode yourself, in Rust, with no Python. Engineering OS runs a continuous agent team on LangGraph that turns GitHub issues into reviewed PRs, asking you twice per item.

The autonomous loop

A long-running project graph in LangGraph feeds a work-item graph per issue. You appear twice per item.

Weekly rhythm

  • Before Monday: scan runs, findings routed
  • Monday: PM drafts the sprint, agents discuss in the workspace, plans posted
  • You approve or trim on the tracking issue
  • Rest of week: build, review, PRs arrive as they finish

Sprint sizing

  • PM sizes freely, no hard cap
  • Tracking issue shows estimate next to recent actual throughput
  • You trim by approving only some items

Discussion

  • Happens in PlanTool's workspace, visible to you
  • GitHub gets the plan, its hash, and a short discussion summary with a link
  • No agent chatter on GitHub

Work-item graph

Fixed transitions are plain code, and roles run in a fixed order, one at a time. The Supervisor is called only when the next step is unclear or stuck.

Review guide attached to every PR

  • What changed and why, linked to the approved plan revision and hash
  • Where to look first, and the riskiest parts
  • How to test it yourself
  • What the AI reviewers found and how each was fixed, round by round
  • Found during review, filed as separate issues
  • Test and CI evidence for the head commit

Work-item states

backlog → ready → leased → running → verifying → review_ready → awaiting_pr_approval → merged → done
blocked · retry_wait · changes_requested · cancelled · failed · stale · recovery_needed

Discussion

  • Turn-based, since only one agent runs at a time
  • Mentions decide who speaks next: @Backend can the API return X?
  • At most 3 rounds per topic, then the PM or Supervisor decides
  • No DMs: every exchange stays in a thread you can read

Instruction layers

  • Base rules agents/base.md: authority, untrusted input, output contract, CLI use
  • Role file agents/roles/<role>.md: duties, limits, definition of done
  • Skills agents/skills/<name>/SKILL.md: the standard skill format Codex, Claude Code and OpenCode read
  • Project conventions: the target repo's AGENTS.md / CLAUDE.md, read from the default branch
  • Task context: issue, approved plan, thread summary

Models

One model at a time

A single global model lease covers cloud and local models alike, so exactly one agent works at any moment and cloud quotas last longer. A LangGraph call holds the lease for one call; a coding run holds it for the whole run, up to a time limit. Ollama models are unloaded (keep_alive: 0) before the next one loads. Urgent work goes first, then sprint order, and work is grouped by model to reduce reloads.

On ChatGPT Plus, Codex is kept for Backend, Frontend and the Reviewer so the 5-hour window lasts. Backend prefers MiniMax and the Reviewer prefers GLM, so the writer and reviewer stay in different families when Codex is used up.

Chain rules

  • Move down on: your budget used up, a provider quota or rate-limit error, or a provider outage after one retry
  • Move back up when a budget window resets
  • Never switch mid-run: checkpoint the attempt, commit work in progress, start the next attempt on the next model with a handoff summary
  • QA and Reviewer skip entries from the family that wrote the code; if none is left, the review guide flags it
  • Every attempt records its model, and the review guide lists them

Allowed providers per project

  • Repo visibility is detected from GitHub at setup and re-checked on every sync, and recorded in the audit log
  • Public and private repos both default to all providers, so every cloud tier is tried before local
  • You can restrict any project; changes need Touch ID and are logged
  • Chain entries for providers that aren't allowed are skipped

Privacy safeguards

  • OpenRouter set to exclude providers that train on prompts
  • Files models never see: .env*, *.pem, *.key, secrets/ plus a per-project list; the sandbox blocks reading them
  • ChatGPT "Improve the model for everyone" reviewed for Codex sessions

The Rust work-item state is a read-only projection of graph events, plus the facts above. Long agent runs never block a worker. The node asks for a dispatch, pauses, and is resumed when the run ends.

Approvals

Plan

  • Approved revisions are immutable files with a SHA-256 hash
  • Task progress lives in SQLite, so ticking work off never invalidates approval
  • Agents report progress with a CLI command against stable task IDs, not by editing checkboxes
  • Adding, removing or rewording tasks creates a new revision and needs approval

PR

  • The App authors the PR so you can review it natively
  • Your approval must be on the current head commit
  • A new commit after approval cancels it
  • PlanTool surface uses a required plantool/policy check instead of a faked review

Always separate

  • Production deploys and high-risk actions
  • Safety stops: retries exhausted, severe findings, privilege escalation, stale approval
  • Agents can never approve, even their own work

GitHub contract

Polling and reconciliation come first; webhooks are an optional speed-up later. Every decision is re-fetched from the API and checked against GitHub user IDs, never usernames.

Native PR review: ApproveYouSatisfies the PR gate for that head commit
  • Plan revisions are new App comments, never edits. The issue body is only an index.
  • Comments from people outside the allowlist are left out of agent context or marked untrusted, even on accepted issues.
  • The App's merge goes through GitHub's API, so branch protection and required checks decide. Setup warns if main lacks protection, required checks, or stale-review dismissal.
  • The release workflow opens a PR for the Homebrew formula instead of pushing to main.

Trust and identity

No system-level changes. No separate macOS user, no VM.

human You

  • Browser signs in with a passkey on localhost
  • Every approval in PlanTool asks for a fresh Touch ID
  • Session cookie is HttpOnly and SameSite strict; no token in the HTML
  • On GitHub you act as your own account
  • One allowlist, managed in PlanTool settings by GitHub username and stored by numeric user ID; anyone on it can approve. Initial member: amritghimire

daemon Authority

  • Holds the App private key in the Keychain
  • Issues short-lived, scope-bound tokens for authorized effects
  • Stop All revokes every in-flight capability

sandboxed Agents and worker

  • CLI calls always carry agent identity; there are no human CLI commands
  • macOS sandbox profile on every Engineering OS run, all four providers
  • Denied: PlanTool's DB and secrets, gh and git credentials, SSH keys, browser profiles, Keychain
  • Allowed: worktree, session documents, model API network, each CLI's own model sign-in files, read access to /nix/store
  • The worker has its own identity, which cannot approve

Remaining risk: an agent you run in Personal mode without the sandbox can still do anything you can. Linux and Windows need their own sandbox backends later.

Data

Clean break. Old ~/.plantool is moved to a backup on first start; no migration.

Consistency rules

  • No transactions across databases: outbox, idempotent inbox, reconciliation on startup.
  • File writes and their database rows are reconciled, since they can't share a transaction: write the file by hash first, then the row; sweep orphans.
  • Every external effect gets an idempotency key and a recorded intent before it runs.
  • Unique constraints: webhook delivery IDs, (provider, external_id) bindings, plan revision numbers per item, (gate, source_event) decisions, one active lease per item.
  • Generation numbers reject reports from cancelled or superseded attempts.

Minimal is the default and matches the loop above. Custom gate editing is deferred until real use of Standard or Strict shows a gap.

Milestone reviews in Standard

  • A project rule (for example migrations, auth, public APIs, CI) suggests [review] tags; the PM drafts them into the plan; you adjust them when you approve the plan
  • At the first milestone stop the App opens a draft PR; each milestone is a comment pointing to its commit, with a compare link from the previous milestone
  • You reply /plantool continue or /plantool request-changes <reason>; approval is tied to that commit
  • CI runs on every milestone commit; after the last milestone the same PR leaves draft for the final PR gate

Repository and Nix

Everything is developed in one repository, plantool. A second, disposable repo, plantool-playground, is where the GitHub App runs end-to-end tests.

Releases

  • One tag ships the binary with the worker inside
  • On first use the worker unpacks to ~/.plantool/worker/<version>/ and runs uv sync --frozen
  • CI fails if the generated contract files are out of date
  • Phases are tracked as GitHub milestones and issues, so the loop can take over its own backlog after Phase 5

Nix

  • Dev shell: Rust, Node, Python, uv, SQLite, gh for people and agents working on PlanTool
  • Package: nix run builds everything, with the worker built from the same uv.lock via uv2nix
  • Agent environments: opt-in per project; if the target repo has a flake.nix, agents build and test inside it
  • Nix is never required for users and is not a security sandbox; the macOS sandbox profile is
  • nix flake check runs in CI

Working on it

  • Keep the installed v0.0.16 as your everyday tool
  • Develop in a checkout with a separate PLANTOOL_HOME and port
  • Install Nix with the Determinate Systems installer; plain rustup, npm and uv still work without it

Deployment on the M1 Max

Tests that must stay green

  • Personal flow without Python, worker down, Phoenix down
  • Forged, bot, edited, stale and replayed approvals rejected; bot-applied labels ignored
  • Approval bound to current plan hash and PR head; new commit cancels it
  • Duplicate dispatch after replay creates no second PR or push
  • Sandboxed agent cannot read secrets; Stop All revokes capabilities
  • Plain "approved" in chat or an issue never opens a gate
  • Two models never hold the lease at once; quota errors move the chain down, window resets move it back up
  • Disallowed providers are never called for a project
